# T2-7 — 기존 entropy/reward 로그 포맷 확인

_source: backlog.json sha256=3780ee2…, schema=1.1 (as of this doc's generation)_

## 목적

REINFORCE 스케줄러의 기존 학습 로그(entropy, reward)를 실제로 살펴보고, 그 파일 형식이 규칙 기반 체크와 Codex CLI 파싱에 적합한지 확인한다.

현재 미확인 사항:
- 로그 파일의 정확한 포맷 (CSV / JSON / 일반 텍스트 / 기타)
- 컬럼 구조 및 구분자
- 파싱에 필요한 정규식이나 파서 구현 가능 여부
- loss, gradient norm은 이미 로깅되는지 (또는 추가 작업이 필요한지)

## 쉬운 설명

설계 단계에서는 "entropy와 reward를 읽어서 이상을 감지한다"고 했지만, 실제로 파일이 어떤 형태인지 모르면 구현을 시작할 수 없다.

예를 들어:
```
# 형식 1: CSV
epoch,entropy,reward,policy_loss,gradient_norm
1,0.85,10.2,2.5,15.3
2,0.84,10.5,2.4,14.8
3,0.83,10.3,2.6,15.1

# 형식 2: 일반 텍스트
Epoch 1: entropy=0.85, reward=10.2, loss=2.5, grad=15.3
Epoch 2: entropy=0.84, reward=10.5, loss=2.4, grad=14.8

# 형식 3: JSON
[
  {"epoch": 1, "entropy": 0.85, "reward": 10.2, "loss": 2.5, "grad_norm": 15.3},
  ...
]
```

이 작업은 실제 로그 파일을 열어 어느 형식인지, 파싱 가능한지 확인하는 것이다.

## 필요한 입력

- 기존 학습 로그 파일 (개인 PC의 학습 출력)
- REINFORCE 스케줄러 코드 (로깅 부분)
- problem.md §3: 현재 로깅 현황 ("entropy, reward만 텍스트로 기록, loss/gradient norm은 미로깅")

## 수행 순서

1. 기존 학습 로그 파일 위치 확인
   - 개인 PC의 스케줄러 코드 실행 결과
   - 파일 경로: 프로젝트 루트 / logs/ / 기타

2. 로그 파일 샘플 수집
   - 첫 5~10줄 이상 확보
   - 정상 run과 이상 run의 로그 모두 (있다면)

3. 파일 형식 분석
   - 텍스트 편집기로 열기

   - 컬럼 순서 및 이름

4. 파이썬 파싱 테스트
   ```python
   import csv
   ```

6. 추가 로깅이 필요한 경우
   - REINFORCE 코드의 어느 부분을 수정해야 하는가?
   - 예상 변경량
