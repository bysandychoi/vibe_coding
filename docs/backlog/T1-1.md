# T1-1 — Windows/PowerShell Hook 동작 검증

_source: backlog.json sha256=3410942…, schema=1.1 (as of this doc's generation)_

## 목적

`backlog.json`의 백로그 기반 작업 관리 체계에서 중추적인 Hook 시스템이 실제로 동작하는지 확인하는 것. 특히 Windows 환경의 PowerShell에서 보호 대상 파일(`data/inspection.csv`)에 대한 삭제/수정/이동 명령이 올바르게 차단되는지 검증해야 함.

## 쉬운 설명

이 프로젝트는 보호해야 하는 중요한 교육용 원본 CSV 파일(`data/inspection.csv`)을 실수로 지우거나 손상되지 않게 두 가지 방어선을 둔다:

1. **권한 벽**: `permissions.deny` 설정으로 CSV 파일에 대한 Edit/Write 도구를 애초에 차단
2. **명령어 감시**: Bash나 PowerShell 명령으로 `rm`, `mv`, `cp`, 또는 리다이렉트(`>`) 같은 파일 수정 명령을 감시해서 차단

이 작업은 **macOS가 아닌 Windows에서, PowerShell 환경에서** 이 감시 기능이 정말로 작동하는지 직접 눈으로 확인하는 것. 즉, 사람이 명령을 내렸을 때 시스템이 `exit 2`(차단 신호)를 반환하고, CSV 파일이 실제로는 손상되지 않았는지를 보는 것이다.

## 필요한 입력

- 적절히 구성된 `.claude/settings.json` (Hook 스크립트 정의 완료)
- Windows 환경과 PowerShell
- Node.js 20 이상
- 기존 `data/inspection.csv` 파일

## 결과물

Hook이 실제로 차단하는지 확인한 구체적인 증거:

- Hook 스크립트의 세 가지 분기(리다이렉트 감시, PowerShell cmdlet 정규식 `Remove-Item`/`Move-Item`/`Set-Content` 등, Bash 토큰 `rm`/`mv`/`sed`/`tee`/`truncate`/`cp`/`del` 등)가 각각 exit 2를 반환하는 로그
- CSV 파일이 어떤 경우에도 실제 손상되지 않았음을 확인
- 정상 파일(`data/sample.csv` 등)에 대해서는 `permissions.deny`가 작동하거나 Hook이 통과하는 것을 확인
- README.md에 Windows 검증 결과와 발견된 한계가 명시됨

## 수행 순서

1. `.claude/settings.json`의 Bash|PowerShell Hook 스크립트(라인 24~31)를 읽어 리다이렉트, cmdlet 정규식, Bash 토큰 등 세 가지 감시 로직을 파악한다.
   - `>` 리다이렉트 감시: `$cmd.Contains('>')`
   - PowerShell cmdlet 정규식: `Remove-Item|Move-Item|Copy-Item|Set-Content|Out-File|Clear-Content`
   - Bash 토큰 목록: `rm`, `del`, `mv`, `cp`, `tee`, `truncate`, `sed`

2. Windows의 PowerShell에서 각 분기를 트리거하는 실제 명령을 실행하면서 exit 코드와 오류 메시지를 캡처한다:
   - 리다이렉트 시도: `echo test > data/inspection.csv`
   - PowerShell cmdlet 시도: `Remove-Item data/inspection.csv`, `Set-Content data/inspection.csv -Value test` 등
   - Bash 토큰 시도: `rm data/inspection.csv`, `mv data/inspection.csv backup.csv`, `sed -i 's/x/y/' data/inspection.csv` 포함 명령

3. 각 경우마다 exit 2와 "BLOCKED" 메시지가 실제로 나타나는지 확인한다.

4. `data/inspection.csv` 내용이 각 시도 후에도 변경되지 않았는지 검증한다.

5. 정상 파일(`data/sample.csv` 등 다른 파일)에 대해서는 Hook이 차단하지 않는지 또는 `permissions.deny`가 적용되는지 확인한다.

6. Edit/Write 도구 경로의 한계(아래 "알려진 한계" 참고)를 문서화한다.

7. README.md의 검증 범위 섹션(라인 15~17)을 확인해 Windows 검증 결과와 한계가 명시되어 있는지 검증한다.

## done_when 확인 방법

**done_when 요구사항**: "차단 로그(exit 2) 캡처 및 정상 파일에서는 차단 안 됨을 확인"

**구체적인 확인 방법**:

1. `.claude/settings.json` 라인 24~31의 PowerShell Hook 스크립트를 읽고, 다음 세 분기 각각에 대한 실제 exit 2 로그 확인:
   - 리다이렉트 분기: `$cmd.Contains('>')` 조건 트리거
   - cmdlet 정규식 분기: 정규식 매칭 트리거
   - 토큰 목록 분기: Bash 토큰 포함 명령 트리거

2. `data/inspection.csv`를 Read로 읽어 변경이 없음을 확인한다.

3. `data/` 폴더 아래 다른 파일(예: 시험용 `data/sample.csv`)에 대해서는 Hook이 차단되지 않거나, `permissions.deny(data/*.csv)`로 차단되는 것을 확인한다.

4. README.md 라인 15~17을 읽어 다음이 명시되어 있는지 확인:
   - "Windows/PowerShell에서는 Bash 경로(rm/mv/sed/tee 등 토큰 매칭, cmdlet 정규식 매칭)의 Hook 스크립트 실행과 차단(exit 2)을 실제로 확인함"
   - "Edit/Write 경로는 `permissions.deny`가 먼저 차단하므로 그 경로의 Hook 스크립트 자체는 permissions 설정을 끄지 않고는 단독 검증이 어려움 — 결과적 보호는 확인됐으나 이 한계는 남아있음"

5. npm run check(또는 PostToolUse Hook)가 통과하는지 확인한다.

## 알려진 한계

**Edit/Write 경로 Hook의 단독 검증 불가**

`.claude/settings.json` 라인 13~21의 Edit|Write|NotebookEdit 분기(이 분기는 `data/inspection.csv` 문자열을 감시하고 BLOCKED 메시지를 출력)는 `permissions.deny` 설정보다 우선순위가 낮다. 실제로는 `permissions` 벽이 먼저 걸리므로:

1. Edit/Write 도구로 `data/inspection.csv`를 수정하려 하면 `permissions.deny(Edit(data/*.csv), Write(data/*.csv))`가 먼저 요청을 차단
2. Hook 스크립트 자체는 실행될 기회를 얻지 못함

결과적으로 파일이 보호되긴 하지만, Edit/Write 경로의 Hook 스크립트가 정말 작동하는지 이 작업에서는 단독으로 검증할 수 없다. 이를 검증하려면 `permissions.deny`를 임시로 비활성화해야 하는데, 그것은 보안 테스트 범위를 벗어난다.

README.md 라인 16에 이 한계가 명시되어 있다.
