## 쉬운 설명

학습 중 이상 감지 체크(로그 파일 읽기, Codex CLI 호출 등)가 매 epoch마다 실행되면 약간의 오버헤드가 생긴다. 따라서 "매 1 epoch마다" 또는 "매 5 epoch마다" 등으로 조절할 수 있어야 한다.

현재 결정:
- 기본적으로는 **매 epoch 체크** (즉시성 중시)
- 조절이 필요하면 **`config.yaml` 파일에서 설정값을 바꿈** (CLI 인자 사용 안 함)
- 이 파일은 다른 모든 T2 결정값(gradient explosion 임계치, 알림 파일 위치, 체크 주기 등)을 한 곳에서 관리하는 공용 설정 파일

체크 주기 조절 방식 설계

1. 조절 방식
   방식: 설정 파일 (config.yaml)
   
   이유:
   - CLI 인자보다 재현성 높음 (여러 실행이 일관됨)
   - 복잡한 설정도 쉽게 관리 (파일 수정만으로 가능)
   - 다른 T2 결정값과 한 파일에서 관리 가능
   - 로그 기반 추적 용이 (설정 파일도 버전 관리 가능)

2. 기본값
   기본값: check_interval = 1 (매 epoch)
   
   근거:
   - "50 epoch 또는 2시간 이내" 감지 목표 달성
   - 체크 작업 오버헤드: 대부분 I/O 대기 (Codex CLI 호출 시간 > 로그 읽기 시간)
   - 매 epoch 체크가 학습 진행을 크게 지연시키지 않을 것으로 예상
   - 필요하면 나중에 config.yaml에서 조정 가능

3. 조절 범위
   최소값: 1 (변경 불가 권장, 하지만 설정으로는 가능)
   최대값: 제한 없음 (사용자가 자유롭게 설정)
   
   권장사항:
   - 1 ~ 50: 일반적 범위 (감지 지연 < 50 epoch)
   - 50 초과: 감지 목표 위험, 권장하지 않음 (but 강제하지는 않음)

4. 공용 설정 파일 (config.yaml) 구조
   
   저장 위치: 저장소 루트(프로젝트 루트와 동일)
   파일명: config.yaml
   형식: YAML
   
   예시 구조:
   ```yaml

   training:
     epochs: 100                  # 기본 학습 epoch 수
     environment: fixed           # 환경 고정

     # baseline 수집 후 problem.md에서 보정
     threshold: null              # baseline 수집 전까지 null

   # T2-3 결정값
   alerts:
     directory: logs/alerts       # 텍스트 파일 저장 위치
     filename_pattern: "{YYYYMMDD}-{HHMMSS}_epoch{NNN}.txt"
     # NNN = 3자리 영점 패딩 epoch 번호
   
   # T2-6 결정값
   anomaly_detection:
     check_interval: 1            # 체크 주기 (epoch 단위)
     # 1 = 매 epoch, 5 = 매 5 epoch, 등

     vanishing:
       window_epochs: 10          # 분석 윈도우
       ratio: 0.01                # baseline 평균 대비 1% 이하
       loss_plateau_ratio: 0.02   # loss 변동폭 < baseline 평균 2%
       warmup_epochs: 5           # 초반 제외 epoch
     
     # Entropy collapse (9.2)
     entropy_collapse:
       window_epochs: 10          # A 조건: 단조 감소 윈도우
       ratio: 0.1                 # B 조건: baseline 평균의 10%
       abs_cap: 0.05              # B 조건: 절댓값 상한 0.05
       drop_window_epochs: 12     # C 조건: 급락 윈도우
       drop_ratio: 0.80           # C 조건: 80% 이상 감소
     
     # Loss-reward 불일치 (9.3)
     loss_reward_mismatch:
       window_epochs: 10          # 분석 윈도우
       reward_change_min: 0.5     # reward 변화량 > baseline std의 50%

5. 로드 순서 및 우선순위
